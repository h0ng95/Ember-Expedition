현재는 첫 비공개 플레이테스트를 준비할 단계다. 전투·성장·연구·저장·첫 조작 안내·스플래시까지 큰 흐름은 연결되어 있다. 앞으로는 실제 사람이 이해하고 즐기는지, 반복 플레이가 성립하는지, 휴대폰에서 기록을 잃지 않고 안정적으로 끝낼 수 있는지를 확인해야 한다.

이 문서는 코드와 v0.32~v0.38 검증 기록을 읽고 정리한 실행 계획이다. 사용자가 개발 순서에 동의해 작업·검증·완료 기준을 아래에 정리했다. 문서의 상태는 실제 구현 및 검증 증거가 있을 때 갱신한다. 아래 수량·성능 목표는 제안이며, 이미 달성한 결과나 업계 공통 기준이 아니다.

진행 순서: 전투 가독성 → 첫 플레이테스트 → 밸런스·안내 보완 → 저장·설정·영어·사운드 → 광고·출시 빌드 → 비공개 테스트와 출시 판단.

진행 상황: 1단계의 전투 화면·최소 진단 기록과 보스 6종의 공격 효과를 v0.39에 구현했다. 구현·검증 결과와 화면을 참고한다. 다음 우선순위는 2단계 사람 플레이테스트다. 실행 체크리스트는 11절, 사람 플레이 기록 양식은 12절에 있다.

2. 가장 먼저 — 전투를 읽을 수 있게 만들기

v0.37에서 이미 발견했지만 아직 적용하지 않은 부분을 우선 처리한다.

  1. 보스 체력·이름·상태를 고정된 정보 영역으로 정리. 날개와 머리 위에 글자가 몰리는 문제를 줄인다.
  2. 피해 숫자와 상태 표시 분리. 짧은 간격의 지속 피해는 표시만 묶고 실제 피해 계산·공격 횟수는 유지한다. 빙결·화상·중독은 아이콘과 형태로도 구분한다.
  3. 어두운 적의 실루엣 보완. 폐광·정원의 적에 필요한 범위만 대비를 조정한다.
  4. 전투 HUD 테마 통일. 거점의 잿빛·금장 테마에 맞추고 전투 예고 문구를 실제 적·행동과 연결한다.
  5. 타격 시점 확인. 검이 닿는 순간, 화살·마법의 발사와 적중, 피해 숫자와 소리가 일치하는지 살핀다. 현재 투사체 경로의 어색함은 점검 후보이며 확정된 버그로 단정하지 않는다.

완료 판단: 사람이 전투를 보고 “누가 얼었는지”, “보스가 무엇을 했는지”, “어느 동료가 먼저 무너졌는지”를 설명할 수 있어야 한다. 1배속·2배속과 후반 밀집 편성에서 모두 확인한다.

3. 사람의 첫 플레이와 난도 검증

먼저 5~8명에게 설명 없이 맡겨 보기

첫 소규모 검토는 문제 발견용이다. 시장 전체 승률을 추정하는 표본으로 쓰지 않는다. 장르 경험이 적은 사람과 익숙한 사람을 섞고, 관찰 중 정답 배치나 조합을 알려주지 않는다.

  • 첫 소환·배치·전투를 외부 설명 없이 할 수 있는가.
  • 동료를 겹쳤을 때 성장·진화·결합의 차이를 이해하는가.
  • 5전투 보스 이전에 필요한 선택을 스스로 했는가.
  • 진 뒤 이유와 바꿔 볼 선택을 말할 수 있는가.
  • 원정 종료 후 다른 조합으로 다시 시작하고 싶은가.
  • 한 원정의 실제 시간, 전투를 보는 시간, 준비에 쓰는 시간은 얼마인가.

난도는 구간·빌드·계정을 나누어 조정

구분 검증할 것
1~2전투 조작을 익히는 여유가 있는가
3~10전투 소환·배치·성장의 첫 선택이 의미 있는가
11~20전투 조합과 전술의 효과가 드러나고 같은 행동의 반복이 지루하지 않은가
21~30전투 앞에서 만든 빌드가 시험받고, 패배가 이해 가능한가
신규·연구 계정 연구가 없어도 공략 가능하며, 연구 완료가 자동 승리를 만들지 않는가
일반 진화·결합 편성 재료·골드를 더 쓴 결합이 특정 역할에서 실질적인 장점을 주는가

v0.34~v0.35 자료에서는 29전투의 보호막·배치 상호작용이 큰 고비였고, 성가 기수 편성은 여러 자동 정책에서 일반 최종 진화보다 불리했다. 자동 정책의 한계를 감안해 이 두 항목을 사람 플레이에서도 우선 확인한다. 공격력 버프의 간접 기여를 개인 피해량만으로 평가하지 않는다. v0.34 비교 · v0.35 후반 분석

목표 제안: 적어도 3종류의 다른 빌드가 Normal에서 현실적인 완주 경로를 갖고, 배치·지출을 무시하는 선택은 후반에서 손해를 본다. 처음부터 적 체력·공격력을 전부 올리지 않고 원인별로 조정한다.

최소 진단 기록

앱 버전·시드·시작 편성·연구 상태·소환/성장/전술 지출·단계별 승패·등불 소모·전투 시간·중도 종료 지점을 남기는 로컬 진단 내보내기부터 추천한다. 이후 원격 분석을 추가한다면 전송 범위와 개인정보 안내를 별도로 설계한다.

4. 추가 개발 — 이해·선택·반복 플레이

출시 전 우선

  • 첫 성장·첫 결합 안내: 실제로 재료가 모였을 때 한 번 보여준다. 최초 실행에 긴 설명을 한꺼번에 넣지 않는다. 기존 1·2전투 안내와 이어지게 한다.
  • 플레이용 동료 도감: 발견한 직업, 역할, 진화 경로, 결합 재료와 결과를 게임 안에서 찾아볼 수 있게 한다. 개발용 시험실을 그대로 공개용 도감으로 쓰지 않는다.
  • 결과의 납득: 기존 전투 기여도와 결과 창을 활용해 피해·회복·보호의 의미를 설명한다. 실제 데이터로 뒷받침할 수 없는 자동 공략 조언은 넣지 않는다.
  • 첫 완주 마무리: 최종 보스 뒤 이야기·완주 기록·다음에 해볼 편성을 연결한다. 이미 있는 원정 기록과 성과를 중심으로 보완한다.

반복 플레이가 단조롭다면 다음으로

소수의 유물 또는 지역 종료 선택 보상을 시범 도입할 수 있다. 예를 들어 6~10개 후보 중 일부를 선택하고, 단순 공격력 보너스보다 표식·보호막·화상·빙결 등 기존 역할을 바꾸는 효과에 집중한다. 이는 미구현 제안이다. 기존 전술·연구와 역할이 겹치는지 먼저 확인하고 한 종류부터 시험한다.

현재 영구 연구는 6노드로 작다. 시작 편성과 공략 방향을 넓히는 연구를 우선 검토한다. 단순 능력치 노드를 대량 추가해 반복 횟수로 난도를 무너뜨리는 구조는 피한다. 해금 조건이 공개되지 않아 원하는 빌드를 시도하기 어려워지는지도 함께 확인한다.

30형태 전부에 대해 기술·대상·사거리·상태 이상·전승·결합 재료·동작·설명 문구의 검사표를 만든다. 무한 빙결, 보호막 반복, 회복 정체로 전투가 풀리지 않는 조건과 시간 초과 처리도 포함한다.

5. 저장·성능·기기 대응

저장과 복구

현재 저장 버전 이행과 손상 감지 검사는 있다. 앱 자체 백업과 기기 간 이전은 없다. 현재 저장 구조

  • 마지막 정상 기록을 복구할 수 있는 백업과 복원 안내 추가.
  • 소환·결합·연구 구매·보상 수령 직전/직후 강제 종료를 시험해 골드·유닛·연구가 유실되거나 중복 지급되지 않는지 확인.
  • 전투 중 종료 후 어디서 재개되는지 규칙을 일관되게 표시.
  • 원정·성과·이야기 저장 도중 중단되어도 데이터 사이의 상태가 어긋나지 않는지 검증.
  • 이전 출시 버전에서 업데이트한 뒤 진행을 이어가는 이행 시험.
  • 앱 삭제·기기 교체 복구를 제공할지 결정하고 실제 제공 범위를 명확히 안내.

첫 출시의 자체 서버와 계정 로그인은 필수로 제안하지 않는다. 로컬 중심 구조로도 시작할 수 있지만, 복구와 기록 이전은 사용자 경험으로 설계해야 한다. SQLite로 바꾸는 것만으로 이 문제가 해결되지는 않는다.

성능과 화면

  • Buddy2에서 원정 반복을 포함한 30~60분 실행: 프레임 시간, 메모리 증가, 발열, 배터리 소모, 앱 멈춤을 측정.
  • 후반 최대 편성·범위 공격·상태 이상이 겹치는 전투에서 1배속과 2배속 확인.
  • Buddy2 외 최신 Android, 다른 화면 비율, 노치·제스처 영역이 다른 기기와 가능한 태블릿 검증.
  • 화면 잠금·홈 이동·전화/알림·이어폰 연결·오디오 복귀·OS의 프로세스 종료 확인.
  • 저사양에서 60fps가 불안정하면 30fps 고정과 효과량 조절을 검토. 평균값뿐 아니라 반복되는 긴 프레임을 본다.

출시 기준 제안: 지원 기기에서 선택한 프레임 목표를 지속 유지하고, 진행을 막는 크래시·저장 유실·중복 보상 등 알려진 중대 결함을 해결한다. 짧은 테스트 중 오류가 없었다는 사실만으로 무결함을 주장하지 않는다.

6. 설정·사운드·영어

  • 공통 설정: 효과음·음악 음량, 언어, 배속 기본값, 필요한 경우 화면 흔들림/섬광 감소. 저장 후 재시작해도 유지.
  • 사운드: 거점·일반 전투·보스의 분위기, 물리/화염/빙결/회복의 구분, 승리·패배·결합의 피드백. 현재 등록된 음원은 기본 합성 효과음 중심이며 BGM 제작은 남아 있다.
  • 영어: UI·직업명·기술·연구·튜토리얼·이야기·오류·광고 안내까지 문자열을 외부화하고 한영 용어집을 일치시킨다.
  • 긴 영어 문장에서 버튼·다이어로그·도감이 잘리지 않는지, 글꼴이 누락되지 않는지 확인. 한국어 UI의 폭을 그대로 고정해 번역만 바꾸지 않는다.
  • 대표 이미지와 게임 내 도트 캐릭터가 같은 인물로 인식되는지, 스토어 그림이 실제 플레이 품질과 동떨어지지 않는지 확인.

현재 전투에는 일시정지와 1·2배속이 있다. 이를 새로 만들 작업으로 중복 계산하지 않는다. 공통 설정 화면과 영어 전 과정은 추가 범위다.

7. 광고 무료판과 광고 없는 유료판

기존 방향인 인앱결제 없음 / 광고 무료 앱 / 별도 광고 없는 유료 앱을 기준으로 한다. 현재 광고 SDK와 판별 배포 설정은 구현되지 않았다.

  1. 같은 게임 코드를 공유하면서 패키지·서명/버전 관리·광고 포함 여부를 분리한다. 유료판에는 광고 SDK도 제외하는 구성을 권한다.
  2. 무료판은 전투 도중 광고를 넣지 않는다. 우선 원정 종료 등 자연스러운 경계에 제한적으로 노출하는 안부터 테스트한다. 노출 주기와 형식은 확정할 작업이다.
  3. 광고가 없거나 로딩에 실패해도 기본 게임이 진행되어야 한다. 광고에서 돌아올 때 화면·오디오·일시정지 상태를 복구한다.
  4. 보상형 광고를 넣는다면 보상 중복/누락을 막고, 무료판과 유료판의 골드·재도전 기회를 어떻게 동등하게 할지 정한다. 현재는 보상형을 확정하지 않는다.
  5. 무료판에서 유료판으로 옮길 때 진행 기록을 가져오는 경로를 설계한다. 다른 앱의 PlayerPrefs가 자동 공유된다고 가정하지 않는다.
  6. 광고 SDK가 다루는 데이터까지 포함해 개인정보처리방침과 데이터 보안 정보를 작성한다. AdMob 채택 시 지역별 동의·개인정보 선택 접근은 UMP 공식 흐름을 검토한다. Google 데이터 보안 안내 · Unity용 UMP 안내

무료·유료 두 앱은 각각 설치·업데이트·광고 유무·기록 이전을 검증해야 한다. 동시 출시가 부담되면 출시 순서를 나누되, 사용자에게 안내할 이전 규칙부터 정한다.

  • Hard 모드, 100전투, 무한 모드.

11. 실행 체크리스트

기존 구현은 1절의 현황을 따른다. 아래 체크박스는 추가 작업과 검증이다. 2026-10-25 v0.39의 완료 범위를 반영했으며, 구현·자동 검사·실기기 확인과 사람 플레이 결과를 구분한다.

2단계 · 첫 플레이테스트

  • 처음 하는 사람 5~8명의 장르 경험·기기·사용 언어를 기록하고 같은 테스트 빌드를 배포한다.

  • 가능한 참여자에게 Normal 한 원정의 종료까지 맡기고, 완주·등불 소진·자발적 종료를 구분한다. 모두가 완주해야 하는 기준은 아니다.

3단계 · 결과 기반 게임성 보완

  • 발견한 난도 고비와 지출 문제를 원인별로 수정한다. 29전투와 결합 편성을 우선 관찰한다.

  • 최종 보스 이후의 이야기·완주 기록·다음 도전 흐름을 점검한다.
  • 반복 플레이 자료를 보고 유물/지역 보상과 연구 확장을 도입할지 판단한다. 추가하기로 한 경우에는 별도 규칙·균형 검증 범위를 작성한다.

4단계 · 제품 완성도와 안정성

  • 정상 저장 백업·복구와 행동/보상 경계에서의 강제 종료·업데이트 이행을 검증한다.
  • 공통 설정·음악/효과음·한국어/영어 전 과정을 완성하고 설정 유지와 문구 잘림을 확인한다.
  • Buddy2 30~60분, 추가 기기·화면 비율·최신 Android, 화면 잠금/복귀·오디오 중단을 시험한다.
  • 기기별 성능 결과를 보고 프레임 목표·효과 옵션·지원 범위를 확정한다.

5단계 · 무료판·유료판과 출시 빌드

  • 광고 형식·노출 시점·보상 여부, 두 상품의 플레이 조건과 기록 이전 방법을 확정한다.
  • 무료/유료 빌드와 무료→유료 기록 이전을 구현하고, 광고 실패·복귀·네트워크 없음 경로를 시험한다.
  • 출시 패키지·서명·버전과 AAB 배포 경로를 만들고 개발용 메뉴/표시를 정리한다.
  • 출시 후보 AAB에서 API·네이티브/광고 SDK 호환·설치·업데이트를 확인한다.

6단계 · 비공개 테스트와 출시 판단

  • Play 계정 유형과 해당 테스트·검토 절차를 확인한다.
  • 출시 후보 빌드로 필요한 비공개 테스트를 진행하고 발견 문제를 수정·재확인한다.
